# このみち（プロトタイプ）

企画書「このみち」の実現性検証用プロトタイプ。出発地・好きな景色（緑/水辺/両方）・使える時間を指定すると、
OpenStreetMap のデータから**出発地に戻ってくる周遊散歩ルート**を自動生成し、ターン案内まで行う。

- 企画書の★機能: ① 緑・水辺ルート検索 ② 所要時間の指定 → 実装済み
- 追加実装: 案内モード（GPS追従・デモ歩行・コース外れ時の引き直し）、計測値の表示（右上のグラフアイコン）

## 動かし方

静的ファイルのみ（サーバー側ロジックなし、APIキー不要）。

```bash
python -m http.server 8765
# → http://localhost:8765/
```

`file://` では動かない（ES Modules と `fetch` のため）。現在地機能は https または localhost で動く。

## 仕組み

| 段階 | ファイル | 内容 |
|---|---|---|
| 取得 | `js/osm.js` | Overpass API から歩行者道・公園/森/草地・水域/河川/海岸線・並木/街路樹を取得。複数ミラーを時間差で並走 |
| 判定 | `js/graph.js` | 道を10mごとにサンプリングし、緑地の内側/縁・水際・並木からの距離で 0〜1 の「緑度」「水辺度」を算出 |
| 探索 | `js/router.js` | 好みに応じたコスト（景観の乏しい道を割増）で A\* 。方位ごとに2〜3点の経由地を置き、所要時間に合う周回を72候補生成→評価→上位3本 |
| 案内 | `js/router.js` | 曲がり角の抽出、現在地のルート上への射影 |
| UI | `js/app.js` | 設定→検索→結果3案→案内 |

評価関数: 好みに触れる道の割合 − 長さのズレ − 同じ道/近接した往復 − 周回の細長さ − Uターン − 曲がり角の多さ。

## 検証結果（`node scripts/test-routing.mjs`）

同梱の5地点 × 好み3 × 時間3（15/30/60分）。生成時間は全条件で約0.2〜1.5秒（ブラウザ・Node 同等）。

| 地点 | 緑に触れる道（全道路比） | 水辺に触れる道 | 30分・両方 の1位 |
|---|---|---|---|
| 京都・四条（鴨川） | 39% | 18% | 緑50% / 水79% |
| 東京・上野（不忍池） | 20% | 3% | 緑100% / 水32% |
| 大阪・中之島 | 27% | 12% | 緑70% / 水62% |
| 横浜・山下公園 | 31% | 16% | 緑51% / 水47% |
| 東京・新宿駅 | 23% | 5% | 緑45% / 水0% |

## 実現性に関する所見

**できること**
- 緑・水辺の「道ごとの度合い」はOSMだけで算出でき、時間内に戻る周回ルートも1秒以内に組み立てられる。
- 川・公園・海沿いの都市では、指定した好みに6〜10割の区間で触れるルートが作れる。
- 名前付きの川・公園を集計して「高瀬川・先斗町公園を巡るコース」のように説明できる。

**課題・リスク**
1. **Overpass 公開サーバーが遅い**: 1地点あたり約30〜50秒（TTFB 30秒超、502も発生）。本番は自前の Overpass/Valhalla/GraphHopper、またはOSM抽出データの事前処理（タイル化）が必須。プロトタイプは事前取得データ同梱＋IndexedDBキャッシュで回避。
2. **場所によっては実現できない**: 新宿は水辺0%、上野で水辺60分コースは12%。UIで「この周辺では水辺がほとんどありません」と正直に出し、別の好みを提案する設計にした。横浜の水辺15分のように条件を満たす候補が0件になる場合もある。
3. **周回の形と景観度のトレードオフ**: 川沿いの往復なら水辺100%でも、きちんとした周回にすると約70〜80%に下がる。「往復OK」の選択肢を用意するか要検討。
4. **評価が自己参照**: 最適化に使うスコアと同じ基準で評価している。「歩いて気持ちよいか」の検証には実地での歩行テスト/ユーザーテストが必要。
5. **OSMデータの偏り**: 街路樹・私有庭・寺社の緑はタグ付けが粗い。水域名が最寄り地物名になるため、川と並行する水路で名前がずれることがある。
6. **案内の品質**: 並行する歩道と車道を行き来する箇所は「引き返す」案内になることがある（現状ルートの約14%）。本番は歩行者ルーティングエンジンの出力を使うのが堅実。
7. **未対応（企画書の将来機能）**: 休憩スポット表示、坂道回避（国土地理院標高タイル）、おすすめ共有、国土数値情報の併用。
